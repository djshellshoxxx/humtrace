# GitHub project landscape for HumTrace

**Reviewed:** 2026-10-08  
**Purpose:** Research notes for engineering, validation, and interface design. This is a survey of public source repositories and their first-party documentation, not an endorsement of their forensic validity and not permission to copy code. Unless a release tag is named, source links point to the live branch as it appeared on the review date; upstream changes can invalidate these observations. Recheck exact source files, licenses, build flags, data rights, and dependencies before any adoption.

## Findings for HumTrace

The most directly relevant open repositories contribute different kinds of evidence. OpenENF and ENFify show concrete approaches and limitations for electrical network frequency (ENF) tamper analysis. Sonic Visualiser and Audacity are strong references for synchronized waveform/spectrogram inspection and annotation workflows. OpenSoundscape supplies a mature research workflow for segment-level annotations, long recordings, and model evaluation, but its bioacoustics models do not establish environmental identity. Pyroomacoustics can make controlled room-response test signals; it cannot establish that simulated rooms predict real recording locations. Praat and Essentia are useful methodological and feature-extraction references, with licensing, dependency, and validation costs that make them poor automatic additions to the core app.

Across these projects, the central engineering lesson is to keep **measurement**, **interpretation**, and **human annotation** separate. Show measurable features and algorithm/version/parameter details; label any match or transition as a hypothesis; allow the analyst to inspect the underlying time-frequency/audio interval; and preserve a user-entered note separately from computed output. An audio feature vector or a similarity score is not a unique physical-location identifier.

## Directly relevant projects

### Open ENF

Repository: [openenf/openenf](https://github.com/openenf/openenf), `master`; README and license viewed 2026-10-08. The repository README describes a cross-platform command-line workflow, TypeScript analysis using an adaptive Goertzel algorithm, and a C# lookup service over TCP. It says grid-frequency lookup data is downloaded separately, limits integrated data to European grids, and states that the tool does not work on 60 Hz recordings. It notes recordings often need to be at least three minutes and that noise or weak grid coupling can prevent a result. Its own README calls results beta and warns that low scores can be hard to interpret; the reported score is not a calibrated probability. [1]

**HumTrace use:** Treat it as an implementation and failure-mode reference for ENF only. Add explicit “no usable ENF,” “reference coverage missing,” and “candidate match” outcomes; keep the reference data source, region, date span, and data license visible. ENF must be an optional detector and must not be presented as a general environmental fingerprint. Do not imply North American grid matching is available unless the app can name and verify a lawful, suitable reference dataset. This source is GPL-3.0; consider the license before any code reuse. Its external grid data is explicitly excluded from the code license. The README's support/coverage statements are upstream statements and should be rechecked before product claims. [1]

### ENFify

Repository: [Licates/ENFify](https://github.com/Licates/ENFify), default branch `main` as observed 2026-10-08. Its README describes phase-based ENF authenticity/tampering classification using a neural network, synthetic and WHU reference examples, generated reports, and experimental VMD/RFA denoising that still needs manual configuration. It says real-world Carioca data was used in testing but is not distributable. The repository advertises MIT licensing. [2]

**HumTrace use:** Study its synthetic authentic/tampered fixture pattern and explicit experimental status for denoising. This is a useful reminder that a clean synthetic test set does not prove performance on field recordings; retain separate synthetic, public real-world, and permissioned/private validation sets, and state which evidence supports each claim. A neural classifier score should not be translated into a probability of editing without calibration on an adequately representative dataset. Since one reference dataset is not redistributable, document how to reproduce tests without it. Do not reuse model weights or sample audio until their separate data and artifact terms are checked; the repository's MIT code license does not automatically license datasets or pretrained assets. The README itself refers to private data and experimental algorithms. [2]

### Sonic Visualiser

Repository: [sonic-visualiser/sonic-visualiser](https://github.com/sonic-visualiser/sonic-visualiser), release **v5.2.1** (tag `sv_v5.2.1`, release commit abbreviated by GitHub as `cf7a16f`, released 2025-03-21), reviewed 2026-10-08. Its README describes a cross-platform desktop application that loads multiple audio formats, presents adjustable spectrograms, waveform views, labeled time points and segments, feature-extraction plugins, imported annotation data, and playback synchronized with the display. The project is GPL-2.0-or-later. Release notes document practical UI issues including high-DPI selection, zoom/scroll responsiveness, display cache behavior, spectrogram rendering cost, shortcut discoverability, and progress dialogs obscuring needed user input. [3][4]

**HumTrace use:** The annotation model is a strong reference for placing evidence at points or spans and keeping overlays synchronized to one time axis. The app should offer waveform and spectrogram together, adjustable time/frequency zoom, cursor readouts, selection-bound measurements, and a labeled event layer. Its release history is a concrete test checklist: hi-DPI pointer alignment, deterministic cache invalidation across zoom, dense-plot performance, progress-dialog focus, and keyboard discoverability. It is GPL, so reuse of source requires an explicit licensing decision; screenshots or design concepts are not a substitute for independent implementation. Music-analysis affordances do not themselves establish forensic reliability. [3][4]

### Audacity

Repository: [audacity/audacity](https://github.com/audacity/audacity), `master` README and project manual accessed 2026-10-08. The project is a mature multitrack editor; the manual's spectral-analysis guidance documents waveform/spectrogram multiview, configurable spectrogram scale, colors, algorithms, and window size. It explains the time-frequency resolution tradeoff. The repository states that the `master` branch is undergoing major structural change for Audacity 4 and directs contributors interested in the 3.x line to a separate branch. The manual currently describes Audacity as GPLv2; check the exact source release and third-party dependencies for redistribution. [5][6]

**HumTrace use:** Use the manual as a usability reference for explaining the window-size tradeoff in plain language and for letting analysts tune display-only settings without silently altering measurement parameters. Make clear whether a control changes the analysis or only the visualization. Keep analysis settings visible and recorded in reports. Audacity is an editor; its presence of spectral tools is not forensic validation of HumTrace measurements. Its moving `master` branch is not a stable integration target. [5][6]

### OpenSoundscape (Kitzes Lab, University of Pittsburgh)

Repository: [kitzeslab/opensoundscape](https://github.com/kitzeslab/opensoundscape), `master`, README and MIT license observed 2026-10-08. The README documents audio loading/trimming, spectrogram generation, Raven annotation import, segment-level prediction tables with start/end times, long-file inference, test directories, tutorials, and model workflows. It identifies the University of Pittsburgh's Kitzes Lab as maintainer. The project is MIT-licensed. It is Python-based and documents Python/PyTorch and optional model packages; the Windows instructions recommend WSL2, which is a caution against assuming a drop-in native Windows dependency. [7]

**HumTrace use:** Study its separation of clip labels, time spans, model scores, and source recording identity; adapt the same conceptual rigor to a deterministic detector result schema. Use it as a reference for annotation-import ergonomics and for building timestamped analysis over long recordings. Its ML classifiers target biological sound labels and are not evidence that an acoustic room or location has been identified. HumTrace should not add those models to its core analysis path. Large optional ML dependencies and third-party model terms would also complicate deterministic offline forensic review. [7]

### Pyroomacoustics (EPFL LCAV research project)

Repository: [LCAV/pyroomacoustics](https://github.com/LCAV/pyroomacoustics), release **0.10.0** documentation linked from upstream, with repository README and MIT license viewed 2026-10-08. The project describes an object-oriented simulator for 2D/3D rooms, a compiled image-source implementation and ray tracing for room impulse responses, plus reference algorithms for STFT, beamforming, direction finding, adaptive filtering, source separation, and single-channel denoising. Its paper describes the package as an evaluation/prototyping framework for acoustic algorithms. [8][9]

**HumTrace use:** Generate controlled test cases with known room dimensions, reflection parameters, source/microphone positions, and simulated impulse responses. Vary one factor at a time (room response, microphone distance, noise, source placement, clipping, codec) to measure detector sensitivity and confounds. Preserve simulator version, seed, and parameters with each fixture. Do not treat simulated reverberation fingerprints as ground truth for real rooms: model assumptions, geometry, materials, microphone responses, and source behavior can diverge from field conditions. The package is Python/C++ and has an MIT license, but pulling it into the native core would still impose build/dependency complexity; prefer an offline corpus-generation harness. [8][9]

### Praat

Praat's [official source-download page](https://praat.org/download_sources.html) links to the project's GitHub source distribution and states that Praat is GPL-3.0-or-later; accessed 2026-10-08. Praat is a long-running research program for phonetics that includes waveform and spectrogram inspection, measurements, and scripting. Its methods are oriented heavily toward speech and phonetic analysis, not environmental-location identification. [10][11]

**HumTrace use:** Use it as a reference for transparent, scriptable analysis procedures and explicit measurement settings, especially when investigating speech-related confounds or reverberation effects on speech. It can be an independent comparison tool for selected acoustic measurements, but only after matching sample rate, channels, window, and method. Do not make Praat a runtime dependency or use its speech-centric measures as a proxy for environment identity. The GPL license is a reuse constraint. [10][11]

### Essentia (Music Technology Group, Universitat Pompeu Fabra)

Repository: [MTG/essentia](https://github.com/MTG/essentia), `master`, accessed 2026-10-08. The repository describes a C++ audio-analysis library with Python bindings and a large algorithm set; upstream documentation includes analysis, segmentation, feature extraction and reference implementations. The repository identifies AGPL-3.0 licensing; confirm the exact license and scope of each module before considering reuse. The project has substantial dependency/build breadth, including codec/FFT options that can change portability and redistribution obligations. [12][13]

**HumTrace use:** Use its algorithm catalogue and implementation as a research cross-check for candidate descriptors (for example, spectral shape, energy, and segmentation) and as a source of questions to test against independent reference implementations. Avoid treating broad algorithm availability as evidence that a descriptor discriminates recording locations. Don't link it into the beta core until the exact license, build options, version, and required dependencies are approved. [12][13]

## Cross-project design and engineering lessons

1. **Keep analysis and display parameters distinct.** A spectrogram's window, hop, scale, range, smoothing, and color map affect what a user sees; some are display-only, while window/hop can alter derived analysis. Label the distinction, persist the actual analysis configuration, and include it in reports. Sonic Visualiser and Audacity expose these controls; their manuals/release notes show why change tracking matters. [3][5]
2. **Make time alignment explicit.** Store all detector outputs in recording-relative sample/time coordinates with stated interval semantics (`[start,end)` preferred), and map them consistently across waveform, spectrogram, event table, and notes. Sonic Visualiser and OpenSoundscape both demonstrate that annotation/prediction outputs are naturally points or spans attached to a recording. [3][7]
3. **Support null/ambiguous results as first-class outcomes.** OpenENF documents realistic no-result cases and the risk of chance matches; report missing prerequisites separately from a negative measurement. Do not force every recording into a cluster or location label. [1]
4. **A numerical score needs semantics.** State whether a value is a raw feature distance, normalized similarity, detector confidence, calibrated probability, or rank. ENFify and OpenENF show why an uncalibrated score should not be phrased as probability. Provide thresholds only with validation evidence and uncertainty reporting. [1][2]
5. **Build independent test fixtures and retain provenance.** Use deterministic synthetic signals and simulation to cover known conditions, but separate them from representative field recordings. Record fixture source, consent/rights, transforms, simulation parameters, labels, and split membership. Never let clips from a single source recording leak across train/validation/test splits if a learned method is used. OpenSoundscape provides segment-oriented data structures; ENFify documents synthetic/public/private data distinctions; Pyroomacoustics supports parameterized synthesis. [2][7][8]
6. **Do not let optional models silently change the forensic baseline.** Keep machine-learning models separate and opt-in. Pin model weights, preprocessing, runtime, and data terms; show model outputs as exploratory evidence with an explicit limitation statement. [2][7]
7. **Make long-file work interruptible and inspectable.** OpenENF describes progress and range narrowing; OpenSoundscape exposes per-window output. HumTrace should provide cancellation, stable partial status, bounded memory, task progress, and reproducible processing of selected intervals. [1][7]
8. **Test plots like measurement instruments.** Cover cursor-to-time/frequency mapping, high-DPI coordinate transforms, channel labeling, resize/zoom cache invalidation, and visual-vs-tabular value consistency. Sonic Visualiser's own release notes show these fail in mature tools too. [3]
9. **Treat citations, data licenses, and software licenses separately.** GPL/AGPL software, freely downloadable data, pretrained model artifacts, and publications each have their own terms. Keep a dependency and dataset manifest for every release. [1][2][3][10][12]

## Suggested research and build sequence

1. Use the existing detector specs to define an immutable `AnalysisRun` record: source hash, source metadata, detector/version, exact settings, time span, numeric outputs, uncertainty/quality flags, and messages. Separate this record from analyst annotations.
2. Build one synchronized UI prototype with waveform, spectrogram, event list, and notes. Use Sonic Visualiser as the strongest interaction reference and Audacity's manual to guide clear time-frequency setting descriptions. Validate keyboard operation, high DPI scaling, zoom, and screen-reader-accessible measurement tables.
3. Expand validation before adding sophisticated classifier behavior: synthetic controlled signals; Pyroomacoustics-generated responses; then licensed field recordings with ground-truth metadata and multiple microphones/positions. Measure false positives for source movement, microphone movement, gain, codec, noise, and edits.
4. Make ENF a separate detector module with explicit regional reference-data availability. Do not claim timestamp verification when reference coverage or signal quality is absent.
5. Consider third-party runtime libraries only after a specific gap is established. Keep Python libraries and room simulators in an offline analysis/corpus harness unless native runtime costs and licensing are justified.
